# 4. Использование CQRS в orders

Date: 2026-10-24

## Status

Accepted

## Context

Изменение заказа и отображение сведений о нём предъявляют разные требования. Операции изменения должны выполнять бизнес-действия с проверкой доменных правил и инвариантов, тогда как чтение должно предоставлять данные в форме, удобной для конкретного пользовательского или системного сценария.

## Decision

Использовать CQRS в bounded context `orders`: разделить обработчики и модели команд и запросов. Команды изменяют состояние заказа, а запросы используют отдельные модели чтения и возвращают DTO, предназначенные для конкретного сценария.

Команды и запросы организуются по сценариям в соответствии с Vertical Slice Architecture, а не по глобальным каталогам `commands/` и `queries/`. Общие доменные правила переиспользуются между срезами.

Модель чтения, возвращаемая query handler, является Application DTO сценария по [общесистемному ADR 6](../../../../docs/adr/0006-ddd-structure-inside-vertical-slices.md#типы-моделей): read-порт возвращает её напрямую, без отдельной копии для каждого слоя. Command-сторона работает с каноническим `Order` из `boundaries/orders/slices/order/domains/order/`.

На начальном этапе обе стороны используют одно хранилище внутри контекста. Конкретная СУБД этим решением не выбирается.

## Consequences

Модели изменения и чтения смогут развиваться независимо в соответствии со своими требованиями, а DTO чтения не будут ограничены формой доменной модели. При этом появятся отдельные обработчики и модели, согласованность которых потребуется поддерживать, хотя использование одного хранилища пока не вводит межхранилищную синхронизацию.

В дальнейшем при необходимости могут быть выделены отдельные проекции. Возможным развитием является событийная проекция `OrderDetails`, объединяющая сведения для карточки заказа; этим ADR она не проектируется и не реализуется.
