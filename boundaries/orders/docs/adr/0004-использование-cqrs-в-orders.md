# 4. Использование CQRS в orders

Date: 2026-10-24

## Status

Accepted

## Context

Изменение заказа и отображение сведений о нём предъявляют разные требования. Операции изменения должны выполнять бизнес-действия с проверкой доменных правил и инвариантов, тогда как чтение должно предоставлять данные в форме, удобной для конкретного пользовательского или системного сценария.

## Decision

Использовать CQRS в bounded context `orders`: разделить обработчики и модели команд и запросов. Команды изменяют состояние заказа, а запросы используют отдельные модели чтения и возвращают DTO, предназначенные для конкретного сценария.

Команды и запросы организуются по сценариям в соответствии с Vertical Slice Architecture, а не по глобальным каталогам `commands/` и `queries/`. Общие доменные правила переиспользуются между срезами.

Модель чтения, возвращаемая query handler, является Application DTO сценария по [общесистемному ADR 6](../../../../docs/adr/0006-ddd-structure-inside-vertical-slices.md#типы-моделей): read-порт возвращает её напрямую, без отдельной копии для каждого слоя. Command-сторона работает с каноническим `Order` из `boundaries/orders/slices/order/domains/order/`.

Обе стороны используют одно хранилище контекста — PostgreSQL `orders`. Query handlers читают свои модели прямо из таблиц и не восстанавливают агрегат `Order` через репозиторий: восстановление агрегата — инструмент command-стороны, его инварианты и форма не должны определять чтение.

### Проекция OrderDetails

Карточка заказа — проекция `OrderDetails` (таблица `order_details`, одна строка на `Order`, колонки `customer_id`, `market_id`, `placed_at` и документ `details` в JSONB; история клиента читается по Market, [ADR 41](../../../../docs/adr/0041-cell-based-architecture-with-control-plane.md)). Её читают Get Order и List Customer Orders; история клиента возвращает полную карточку каждого заказа, поэтому читателю истории (BFF) не нужен `GetOrder` на каждый заказ. Cancellation Window не хранится: его считает политика в момент чтения.

- **Когда обновляется.** Репозиторий пишет строку в транзакции каждого изменения `Order` (`Add`, `Save`) — и use cases API, и consumer'а integration events, и Temporal Activities. Проекция не отстаёт от `Order`: клиент сразу видит свой только что оформленный заказ. Асинхронная проекция из Kafka здесь не нужна: все данные карточки — данные `orders`, а `orders` не публикует событий на каждое изменение.
- **Снимок названий.** Название Menu Item сохраняется в `order_items.name` при Place Order вместе с ценой: дальнейшие изменения меню не меняют оформленные заказы. У заказов, оформленных до этого, названия нет (`NULL`, в карточке — пустое): из текущего меню оно не подставляется.
- **Версии.** Строка хранит `order_version` (версия `Order`, которую она отражает) и `projection_version` (форма документа, `OrderDetailsProjectionVersion` в коде). Строка более новой версии `Order` никогда не перезаписывается более старым снимком.

### Перестроение проекции

Проекция — чистая функция таблиц `orders`, `order_items`, `order_transitions`, поэтому перестраивается из них без replay событий.

- **Catch-up при старте.** Каждый процесс после миграций проецирует заново заказы без строки, со строкой другой `projection_version` или другой версии `Order`. Процессы сериализуются advisory lock: второй ничего устаревшего не находит. Это покрывает и первичное заполнение после миграции, и изменение формы документа: новая форма — новый `OrderDetailsProjectionVersion`, и строки догоняются на первом старте новой версии.
- **Ручное перестроение.** `orders-admin projections rebuild order-details` проецирует заново все заказы — ремонт после дефекта проектора без смены версии; `orders-admin projections catch-up order-details` — тот же catch-up, что при старте, по требованию.
- Перестроение идёт пачками по `id`, каждый заказ — в своей транзакции под `FOR SHARE` строки `orders`: параллельное изменение ждёт и не теряется.
- **После выкатки.** Во время rolling update старые pods меняют `Order`, не зная о проекции или о новой форме документа, — и после catch-up на старте новых pods. Такое бывает только при выкатке, которая вводит проекцию или меняет `projection_version`; эти строки догоняет `orders-admin projections catch-up order-details` после выкатки или старт следующего pod. Периодического прохода нет: в остальное время проекция пишется в транзакции изменения и отставать ей нечему. Несовместимое изменение формы, которое новые читатели не прочтут в старых строках, делается через expand/contract: новая таблица и её catch-up, переключение чтения следующим релизом, удаление старой таблицы после него.

## Consequences

Модели изменения и чтения смогут развиваться независимо в соответствии со своими требованиями, а DTO чтения не будут ограничены формой доменной модели. При этом появятся отдельные обработчики и модели, согласованность которых потребуется поддерживать, хотя использование одного хранилища пока не вводит межхранилищную синхронизацию.

Карточка и история читаются одним запросом к `order_details`; BFF больше не читает меню ради названий позиций и не делает `GetOrder` на каждый заказ истории. Цена — вторая запись в каждой транзакции изменения `Order`, catch-up на старте процесса (время старта растёт с числом устаревших строк) и правило: каждая новая запись в `orders`, `order_items` или `order_transitions` вне `Add`/`Save` обязана обновить проекцию, иначе строка отстанет до catch-up.
