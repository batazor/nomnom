## Context

Проект учебный, и Event Sourcing в нём ещё не пробовали. Сейчас состояние `Payment` и `Payment Operation` хранится текущими строками в `payments` и `payment_operations`, а история видна только через операции: что происходило с самим `Payment`, восстановить нельзя.

`Payment` подходит для первого опыта лучше других агрегатов:

- поток короткий: обычный заказ даёт 7–10 событий;
- для денежной операции журнал фактов полезен сам по себе;
- у `Order` процессом уже управляет Temporal, и второй журнал создал бы два источника правды о процессе;
- FSM по ADR 21 уже чистая, поэтому `decide` и `evolve` строятся поверх неё.

Текущая модель мешает в одном месте. `Payment` и `PaymentOperation` — отдельные агрегаты со своими версиями, хотя результат provider меняет оба в одной транзакции, а правило «не больше одной незавершённой операции» охватывает оба и держится на индексе.

## Decision

### Источник истины

Источник истины для `Payment` — его поток в таблице `payment_events`. Таблицы `payments` и `payment_operations` становятся синхронными проекциями. Event store написан в контексте на psycopg, без библиотеки: схема маленькая, SQL остаётся явным (ADR 39), а `domains/` не зависит от базового класса фреймворка.

### Один агрегат и один поток

`PaymentOperation` становится сущностью внутри агрегата `Payment`, и на один `Payment` приходится один поток. Правило одной незавершённой операции проверяет сам агрегат, а результат provider пишется в поток одним commit. Отдельная версия и репозиторий операции исчезают. Операция по-прежнему ищется по `operation_id` и idempotency key: проекция даёт `payment_id`, затем загружается поток.

### Decider

```text
decide(state, command) → events | typed domain error    чистая, использует FSM (ADR 21)
evolve(state, event)   → state                          чистая, без бизнес-правил
```

Класс `Payment` остаётся тонкой оболочкой: его методы вызывают `decide`, применяют `evolve` и накапливают новые события и transitions для `pull_events` и `pull_transitions`. Поэтому handlers, Outbox и telemetry работают как раньше. При восстановлении из потока события и transitions не накапливаются: повторно ничего не публикуется и не считается.

### Хранилище

```text
payment_events    (payment_id, version, event_type, schema_version, payload JSONB, traceparent, recorded_at)
                  PRIMARY KEY (payment_id, version)
payment_snapshots (payment_id PK, version, schema_version, state JSONB, recorded_at)
```

- Optimistic concurrency обеспечивает первичный ключ: при гонке второй писатель вставляет занятую версию и получает `ConcurrencyConflictError`, который UoW повторяет по ADR 20. Advisory locks не нужны, поэтому режим PgBouncer на это не влияет.
- Поток неизменяем: `UPDATE` и `DELETE` строк `payment_events` отклоняет триггер.
- `payload` — JSONB, потому что Domain Event внутренний и контрактом не является. Protobuf и Schema Registry остаются для Integration Events (ADR 25). Суммы хранятся строками, без потери точности.
- `event_type` — явное имя из реестра, а не имя Python-класса: переименование класса не ломает историю.
- Старое событие читается через upcaster по `(event_type, schema_version)`. Неизвестный тип или версия — ошибка, а не пропуск.

Первое реальное изменение схемы — `requested_by` в `PaymentOperationRequested`, версия 2: кто запросил операцию (`kind`, `id`, `delegate`). Upcaster дополняет событие версии 1 значением `null`, которое означает «неизвестно, записано до появления поля»: подставлять значение вроде `system` нельзя, это выдумало бы факт. `requested_by` живёт в потоке и состоянии операции, а наружу не выходит: gRPC, проекции и Integration Events не меняются. Идентификатор пользователя теперь хранится в неизменяемом журнале, поэтому удалить его по запросу нельзя; для учебного проекта это принято, в боевой системе понадобился бы crypto-shredding или псевдоним.

### Снапшоты

Снапшоты предусмотрены сразу, хотя на текущих потоках не дают заметного выигрыша. Они нужны, чтобы отработать механику и не перестраивать чтение, когда потоки вырастут, например с частичными Capture и Refund.

- `payment_snapshots` хранит только последний снапшот `Payment`. Это производные данные: удаление таблицы не теряет информацию.
- Снапшот пишется в той же транзакции, что и события, когда commit пересекает границу `EVENT_STORE__SNAPSHOT_EVERY`: `floor(новая версия / N) > floor(старая версия / N)`. Commit из нескольких событий поэтому границу не пропустит.
- Ошибка записи снапшота откатывает транзакцию. Молча пропускать её нельзя: в той же базе это означает сбой всей транзакции.
- Загрузка: снапшот, затем события с `version` больше версии снапшота, затем `evolve`. Сначала читается снапшот, потому что поток только дописывается и более позднее чтение его хвоста ничего не пропустит.
- Снапшот с другим `schema_version` не используется: состояние собирается из всего потока, а следующая граница его перезаписывает. Это пересборка производных данных, а не запрещённый фолбек: источник истины один и тот же, результат идентичен. Нечитаемый снапшот текущей версии — дефект и явная ошибка.
- `EVENT_STORE__SNAPSHOT_EVERY` — обязательное положительное целое: пустое или невалидное значение завершает процесс на старте. В окружениях значение задаётся явно; в kind это 5, чтобы механизм реально работал на обычном заказе.
- Изменение формы состояния или `evolve` требует поднять версию снапшота. Тест сверяет для записанных потоков, что загрузка со снапшотом на каждой версии равна полному replay.

### Проекции и уникальность

Репозиторий обновляет проекции из состояния агрегата в той же транзакции, что и запись событий. Запросы `Get Payment Status`, `List Payment Operations` и e2e-проверки по `payments` не меняются.

Правила между потоками остаются на индексах проекций: `UNIQUE (order_id)` и `UNIQUE (idempotency_key)`. Сохранение идёт в savepoint, поэтому дубликат откатывает и уже вставленные события: поток без проекции не остаётся.

### Outbox и Integration Events

Контракты, топик и Outbox не меняются (ADR 13, 25, 37). `PaymentCreated` и события операций не входят в allowlist mapper'а и не публикуются. `provider_reference` появляется в доменном `PaymentAuthorized`, но не в контракте.

`aggregate_version` теперь равна версии потока после commit. Она по-прежнему растёт между commit, но растёт уже не обязательно на 1: операции добавляют версии без публикации. Детерминированный `event_id` остаётся уникальным. Сейчас `aggregate_version` событий `payments` никто из consumers не проверяет.

`payment_events` не входит в Debezium publication: наружу по-прежнему уходит только Outbox.

### Пересборка проекций

Проекции и снапшоты — производные данные, и это проверяется операторской командой `payments-admin` (разовый запуск в образе процесса, как у `orders-admin`):

- `projections rebuild [--snapshots]` очищает `payments` и `payment_operations`, а по флагу и `payment_snapshots`, и заполняет их заново из потоков в одной транзакции. Таблицы держит `EXCLUSIVE`-блокировка: запросы читают прежние строки до commit, записи ждут, поэтому уникальность `order_id` и `idempotency_key` не остаётся без защиты. Ожидание блокировки ограничено 5 секундами, чтобы команда падала, а не вставала за чужой длинной транзакцией.
- Потоки читаются полностью, без снапшотов: иначе ошибка снапшота попала бы в проекцию. Снапшот пишется на последней кратной версии потока.
- Нечитаемый поток или расхождение числа строк откатывают всё: частичной пересборки нет.
- `projections check` сравнивает производные данные с потоками в одном снимке базы и ничего не меняет. Снапшот другой версии схемы пропускается: при загрузке он и так не используется. В вывод попадают только ключи и вид расхождения, значения нет: в них есть данные provider.

Outbox не затрагивается, поэтому повторной публикации нет. Цена — записи ждут на время пересборки, а UoW повторяет конфликты недолго: часть операций может завершиться ошибкой и должна быть повторена вызывающей стороной. Для учебных объёмов этого достаточно; сборка рядом с заменой таблиц сложнее и здесь не нужна.

### Существующие данные

Перенос не делается: боевых данных нет. Миграция завершается ошибкой, если `payments` не пуста, чтобы не получить `Payment` без потока. Хранилище kind перед выкаткой сбрасывается вместе с незавершёнными заказами.

### Отклонённые варианты

| Вариант | Почему нет |
| --- | --- |
| Отдельные потоки `Payment` и `PaymentOperation` | Результат provider пишется в два потока, а правило одной незавершённой операции снова уходит в индекс |
| Журнал рядом с текущими таблицами, которые остаются источником истины | Это аудит, а не Event Sourcing: replay и версионирование остаются непроверенными |
| Python `eventsourcing` | Зрелая библиотека, но её `Aggregate` приходит в `domains/`, а собственные таблицы нужно сочетать с UoW и Outbox. Сравнить можно позже на готовых тестах поведения |
| KurrentDB | Новая инфраструктура и отдельная транзакция: атомарность с проекциями и Outbox теряется, лицензия собственная |
| Kafka как event store | Нет проверки версии по ключу при записи, инварианты не защитить |
| Dynamic Consistency Boundary | Отдельный эксперимент: инварианты `Payment` укладываются в один поток |
| Асинхронные снапшоты | Нужен процесс и наблюдение за отставанием ради данных, которые в той же базе пишутся одним `INSERT` |
| История снапшотов | Чтение любой версии дешевле и точнее собирается из потока |

## Consequences

Появляется полная история `Payment`, состояние можно восстановить на любую версию, а новые read model можно строить из событий. Проект получает реальный опыт replay, upcasting, снапшотов и конфликтов версий. Первичный ключ заменяет отдельные проверки версий `Payment` и `PaymentOperation`.

Цена:

- запись дороже и шире: события, проекции, иногда снапшот в одной транзакции;
- любые две записи в один `Payment` теперь конфликтуют и повторяются через UoW;
- события неизменяемы, поэтому ошибка в модели исправляется новыми событиями и upcaster'ами, а старые форматы поддерживаются всегда;
- снапшоты пока усложняют код сильнее, чем ускоряют его, и требуют дисциплины с версией схемы.

Не входит в решение: запись subject в событиях для аудита, Event Sourcing в других контекстах.
