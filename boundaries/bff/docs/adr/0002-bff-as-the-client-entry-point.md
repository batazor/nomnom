# 2. BFF as the Client Entry Point

Date: 2026-10-24

## Status

Superceded by [3. Use WunderGraph Cosmo for the BFF](0003-use-wundergraph-cosmo-for-the-bff.md)

## Context

Mobile- и web-клиентам nomnom нужен стабильный публичный API, спроектированный вокруг пользовательских сценариев и не раскрывающий внутренние адреса, Protobuf-контракты или топологию сервисов. Внутреннее синхронное взаимодействие уже определено через gRPC и BSR в [общесистемном ADR 7](../../../../docs/adr/0007-grpc-contracts-and-buf-schema-registry.md), но это решение не задавало внешний клиентский интерфейс и границу доверия.

Клиентские сценарии могут требовать данных нескольких bounded contexts. При этом бизнес-модель, данные, инварианты и авторизация конкретных доменных действий должны оставаться у сервисов-владельцев. Длительный процесс заказа уже принадлежит `orders` и оркестрируется через Temporal; клиентский HTTP-запрос не должен становиться временем жизни этого процесса.

## Decision

### Единая клиентская точка входа

Создать один отдельный сервис BFF как единую прикладную точку входа для клиентского API. Mobile- и web-клиенты обращаются только к его публичному HTTPS/JSON API. Контракт будет описан OpenAPI, а версия задаётся префиксом `/v1`.

Внутри `/v1` разрешены только обратно совместимые аддитивные изменения. Нельзя удалять поля, менять их тип или смысл либо добавлять обязательные поля запроса для существующих клиентов. Несовместимое изменение требует новой версии API.

Один BFF обслуживает текущие mobile- и web-сценарии. Основанием для выделения отдельных BFF станет устойчивое расхождение их сценариев и требований; сейчас этот критерий не выполнен. Единая точка означает единый логический API, а не один процесс: сервис может иметь несколько реплик. BFF не хранит между запросами пользовательские сессии или состояние бизнес-операций; допустимы пулы соединений и технические кэши, например кэш ключей проверки JWT.

Завершение внешнего TLS, rate limiting и базовая защита от злоупотреблений находятся на edge ingress/gateway. BFF является первой прикладной точкой. Защита внутренних соединений через mTLS будет описана отдельно.

Область решения ограничена клиентским API. Платёжные webhooks обслуживаются интеграционными адаптерами `payments`. Health checks, metrics и другие служебные интерфейсы используют отдельные технические маршруты и правила доступности.

### Ответственность и граница доверия

BFF:

- проверяет структуру, типы и обязательные поля клиентского запроса; семантическая валидация и допустимость доменной команды остаются в сервисе-владельце;
- проверяет access token доверенного OAuth 2.0/OIDC-провайдера; для JWT проверяются подпись, допустимый алгоритм, issuer, audience и срок действия; ID token не принимается как access token;
- проверяет общие ограничения доступа к клиентскому сценарию;
- формирует доверенный пользовательский контекст — subject, роли/scopes и tenant — только из проверенных данных аутентификации; одноимённые клиентские заголовки не являются доверенным источником;
- передаёт этот контекст внутренним сервисам через gRPC metadata;
- направляет команду сервису-владельцу операции, агрегирует ответы нескольких сервисов и преобразует их в клиентские DTO;
- задаёт единые форматы ошибок, cursor-based пагинации списков и метаданных ответа;
- продолжает W3C Trace Context, включая `traceparent`, и передаёт request ID, deadlines и cancellation через соответствующие механизмы HTTP/gRPC; BFF проверяет или создаёт request ID и возвращает его клиенту;
- принимает `Idempotency-Key` для изменяющих запросов и передаёт его сервису-владельцу.

Внутренний сервис доверяет утверждённому BFF пользовательскому контексту только при вызове от аутентифицированной и явно авторизованной identity BFF. mTLS подтверждает identity вызывающей стороны, политики доступа разрешают этой identity передавать контекст, а сетевые политики ограничивают доступность сервисов. Прямой доступ клиентов к внутренним gRPC/Connect API исключён.

Это правило относится к вызовам BFF и не запрещает необходимые межсервисные взаимодействия: у них собственные правила аутентификации и делегирования контекста. Права на конкретные доменные действия, принадлежность ресурсов и tenant-изоляцию всегда проверяет сервис-владелец.

### Границы доменной ответственности

BFF — прикладной сервис для клиентских сценариев, а не bounded context. У него нет собственной доменной модели или хранилища доменных данных. Клиентский API проектируется вокруг сценариев и экранов и не обязан повторять внутренние RPC один к одному.

Бизнес-инварианты выполняются в доменной модели соответствующего контекста, а команда направляется сервису-владельцу операции. BFF получает доменные данные только через gRPC API владельцев: он не читает чужие БД, не публикует и не потребляет Kafka-сообщения, не запускает и не управляет Temporal workflow. Длительный процесс заказа выполняется в `orders`; BFF только готовит клиентский запрос и ответ и координирует синхронные вызовы в рамках клиентского сценария.

Агрегация создаёт единое клиентское представление, но не обеспечивает общую транзакцию или атомарный снимок данных нескольких сервисов. Источниками истины остаются сервисы-владельцы.

### Внутреннее gRPC-взаимодействие

BFF вызывает внутренние сервисы через их gRPC API согласно общесистемному ADR 7. В будущем для сервиса будет создан один `boundaries/bff/infrastructure/grpc/buf.gen.yaml`. Каждый потребляемый модуль из `buf.build/nomnom` закрепляется неизменяемым BSR commit непосредственно в `inputs[].module`, например:

```yaml
inputs:
  - module: buf.build/nomnom/orders:<commit-id>
```

Отдельное поле `ref` для module input не используется. Generated code будет коммититься; инфраструктурные адаптеры слайсов используют общие сгенерированные клиенты без собственных копий. Выбор языка, генераторов и runtime относится к следующему шагу.

### Организация слайсов

BFF использует Vertical Slice Architecture. Слайсы соответствуют клиентским сценариям, например `checkout`, `order-tracking` и `restaurant-catalog`:

```text
boundaries/bff/
  <slice>/
    applications/
    infrastructure/
  infrastructure/
    grpc/
```

`applications` содержит сценарии, подготовку клиентских представлений, агрегацию, координацию вызовов и интерфейсы необходимых зависимостей. `infrastructure` содержит HTTP-обработчики, gRPC-адаптеры, преобразования транспортных типов и технические интеграции. Слоя `domains` нет: агрегаты и бизнес-правила остаются в bounded contexts. HTTP-, gRPC- и Protobuf-типы не становятся моделями `applications`.

### Создание заказа

1. Клиент отправляет `POST /v1/orders` с `Idempotency-Key`.
2. BFF проверяет формат запроса, access token и общие ограничения доступа, затем формирует пользовательский контекст.
3. BFF вызывает API создания заказа в `orders`, передавая контекст, ключ идемпотентности и deadline.
4. `orders` проверяет доменные правила и права, обеспечивает идемпотентность и подтверждает надёжное принятие команды, возвращая идентификатор заказа и статус.
5. BFF возвращает `202 Accepted` с идентификатором, статусом и `Location: /v1/orders/{id}`.

HTTP-запрос завершается после подтверждения от `orders`; workflow продолжает собственный жизненный цикл. Разрыв соединения или таймаут не доказывает, что заказ не создан, а отмена RPC не откатывает принятую команду и не отменяет workflow. Неопределённый результат разрешается повтором с тем же ключом идемпотентности. Отмена заказа является отдельной доменной командой. Изменение статуса клиент узнаёт через polling `GET`; push-уведомления находятся вне области этого ADR.

### Просмотр заказа

1. Клиент отправляет `GET /v1/orders/{id}`.
2. BFF получает обязательные данные из `orders`, который проверяет доступ к заказу.
3. При необходимости BFF получает дополнительные сведения из `restaurants` и `delivery`. Независимые вызовы выполняются параллельно после получения необходимых идентификаторов.
4. BFF формирует клиентский DTO согласно заранее заданной политике частичных результатов.

Зафиксированные данные заказа берутся из `orders`: например, стоимость не пересчитывается по текущим ценам ресторана. Актуальные дополнительные сведения не заменяют исторические данные заказа.

### Бюджет времени и отмена

Каждый сценарий получает общий бюджет HTTP-запроса. Deadline каждого gRPC-вызова ограничивается оставшимся бюджетом и лимитом зависимости. Повторы и backoff входят в тот же бюджет; часть времени резервируется на формирование HTTP-ответа. Отмена клиентского запроса передаётся незавершённым синхронным вызовам, где применимо. Конкретные значения определяются требованиями сценария.

Отмена RPC не означает откат выполненных изменений и не отменяет принятый workflow.

### Ошибки

Публичные ошибки используют RFC 9457 Problem Details и `Content-Type: application/problem+json`. Ответ содержит `type`, `title`, `status`, безопасный `detail` и расширение `requestId`; `status` совпадает с HTTP-статусом.

`google.rpc.ErrorInfo` преобразуется через явное соответствие `(domain, reason)` стабильному URI публичного типа ошибки. `detail` строится из безопасного описания и разрешённых данных, а `metadata` переносится только по allowlist. Неизвестные причины получают общее безопасное описание. Необработанные внутренние сообщения, stack traces, адреса и топология сервисов клиенту не возвращаются.

Базовая политика отображения:

| gRPC status | HTTP status |
| --- | --- |
| `InvalidArgument`, `OutOfRange` | `400 Bad Request` |
| `Unauthenticated` | `401 Unauthorized` |
| `PermissionDenied` | `403 Forbidden` |
| `NotFound` | `404 Not Found` |
| `AlreadyExists`, `FailedPrecondition`, `Aborted` | `409 Conflict` |
| `ResourceExhausted` | `429 Too Many Requests`, если превышен лимит клиента |
| `DeadlineExceeded` | `504 Gateway Timeout` |
| `Unavailable` | `503 Service Unavailable` |
| `Unimplemented` | `502 Bad Gateway`, если публичный сценарий поддерживается, но необходимый внутренний RPC недоступен |
| `Internal`, `Unknown`, `DataLoss` | `500 Internal Server Error` |

Исключения:

- исчерпание инфраструктурной ёмкости, включая `ResourceExhausted` без подтверждённого превышения клиентской квоты, возвращает `503`;
- `401` и `403` относятся к аутентификации и правам пользователя; ошибка credentials или разрешений самого BFF при внутреннем вызове возвращает безопасный `502`;
- для `Cancelled` учитывается причина: при разрыве клиентского соединения ответ уже не отправляется, при исчерпании общего бюджета возвращается `504`, если соединение открыто, а неожиданная отмена зависимостью даёт `502`; публичный `499` не вводится.

### Частичные результаты

Для каждого агрегирующего сценария заранее определяются обязательные данные и optional enrichment. Данные владельца основной сущности обязательны, и ошибка их получения завершает весь запрос. При временной недоступности заранее объявленного optional enrichment соответствующее поле отсутствует, а `200 OK` содержит `meta.partial: true` и список пропущенных публичных полей в `meta.omittedFields`.

Частичные результаты не маскируют ошибки доступа или валидации. Метаданные не раскрывают внутренние имена сервисов. `206 Partial Content` для агрегации не используется.

### Повторы и идемпотентность

Read-only RPC могут повторяться только при оговорённых временных ошибках, с ограничением попыток и backoff/jitter в пределах общего бюджета.

Изменяющие RPC повторяются только при наличии `Idempotency-Key` и документированной гарантии сервиса-владельца. Одинаковые ключ и запрос соответствуют одной операции и не создают повторный заказ или workflow; тот же ключ с другим содержимым возвращает `409 Conflict`. Область ключа включает операцию и пользовательский/tenant-контекст. Дедупликация и её данные принадлежат сервису-владельцу, а срок действия ключа задаётся контрактом операции. Само наличие заголовка не гарантирует безопасный повтор.

### Наблюдаемость

Требуются сквозные traces от HTTP до внутренних вызовов, метрики по клиентским сценариям и структурированные логи с request ID. Ошибки зависимостей, повторы и частичные ответы должны быть различимы. Токены и чувствительные данные в логи не записываются.

## Consequences

Клиенты получают единый стабильный API, не зависящий от внутренней топологии и транспортных контрактов. BFF централизует общие прикладные правила клиентской границы, формирует доверенный контекст и позволяет собирать представления нескольких сервисов, не перенося в себя доменную модель.

Цена решения — дополнительный сетевой переход, необходимость проектировать бюджеты времени, error mapping и политику частичных результатов для каждого сценария, а также эксплуатация общего компонента. Горизонтальное масштабирование требует сохранять BFF stateless. Агрегированные ответы могут содержать данные разных моментов времени и не дают межсервисной атомарности.

Этот ADR описывает архитектурные требования, но не означает, что BFF уже реализован. Следующие шаги: выбрать язык и фреймворк, создать OpenAPI-спецификацию и конфигурацию генерации, реализовать слайсы и технические интеграции, а отдельно — спроектировать push-уведомления о статусе заказа и защиту внутренних соединений mTLS.
