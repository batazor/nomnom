# 40. Кеширование чтений: Valkey, cache-aside с TTL, инвалидация через CDC по необходимости

Date: 2026-10-26

## Status

Accepted

Обобщает правило о кеше authorization-решений из
[18. SpiceDB for Authorization](0018-spicedb-for-authorization.md#failures-caching-и-observability)
на все контексты. Опирается на [17. Cloud-native runtime](0017-cloud-native-application-runtime.md),
[26. k6](0026-k6-for-performance-testing.md),
[36. GraphQL subscriptions](0036-graphql-subscriptions-via-cosmo-streams.md) и
[37. Доставка Outbox через Debezium CDC](0037-outbox-delivery-via-debezium-cdc.md).
Первый кеш — [локальный ADR 3 `restaurants`](../../boundaries/restaurants/docs/adr/0003-catalog-read-cache-in-valkey.md).

## Context

Сервисы читали только из своих хранилищ (ADR 8). Самый нагруженный путь чтения — публичный
каталог `restaurants`: `GetRestaurant`, `GetMenu` и `ListRestaurants` вызывают UI через BFF и
Place Order контекста `orders` на каждый заказ, а меняется каталог редко. Кеш вводится сразу, не дожидаясь
capacity-прогона. Чтобы следующие кеши не появились как dual write с TTL «на глаз», правила
общие для всех контекстов.

Кеш — вторая копия данных: у неё есть окно устаревания, инвалидация и свои отказы. Поэтому
решение задаёт, что кешировать можно, а что нельзя, как инвалидировать и как вести себя при
недоступном кеше.

## Decision

### Что можно кешировать

Кеш вводит локальный ADR контекста-владельца данных. Он описывает:

- что кешируется, ключи и их кардинальность, TTL;
- допустимое окно устаревания и то, что видит пользователь внутри него;
- нужна ли инвалидация или достаточно TTL;
- выдержит ли хранилище нагрузку без кеша, когда Valkey недоступен;
- метрики и ожидаемый hit ratio.

Выигрыш проверяется прогоном k6 с зафиксированным состоянием кеша (cold/warm, ADR 26); если
выигрыша нет, кеш удаляется.

### Что не кешируется

- Состояние, на которое опирается команда: агрегат внутри Unit of Work, проверки инвариантов.
  Команды читают только из хранилища.
- Inbox, Outbox, ключи идемпотентности, workflow state Temporal и любое другое durable state
  (ADR 17): потеря кеша не должна нарушать корректность.
- Чужие данные. Контекст кеширует только данные, которыми владеет; кеш не становится каналом
  интеграции и не читается другими контекстами (ADR 8).
- Чтения, которые перечитываются по Change Notification (ADR 36), если пользователь должен
  сразу увидеть изменение: Router перечитывает сущность сразу после уведомления и получит
  кешированное старое состояние. Поэтому не кешируется `GetOrder` в `orders`. Если устаревание
  на TTL допустимо (открытие ресторана на kitchen board, локальный ADR 3 `restaurants`), это
  записывается в решении о кеше.
- Authorization-решения SpiceDB — только по условиям ADR 18, отдельным решением.

### Технология

- **Сервер — [Valkey](https://valkey.io/)** (BSD-3-Clause, wire-совместим с Redis), а не Redis:
  лицензия Redis сменилась на RSAL/SSPL и затем AGPL. Версия — актуальная стабильная на
  момент ввода, совместимость подтверждается прогоном.
- **Go-клиент — [rueidis](https://github.com/redis/rueidis)**, а не go-redis: client-side
  caching поверх RESP3 `CLIENT TRACKING`, автоматический pipelining и OpenTelemetry через
  `rueidisotel`. Клиенты других языков выбирает локальный ADR контекста, который первым вводит
  кеш на этом языке: TS — [iovalkey](https://github.com/valkey-io/iovalkey) (локальный ADR 3
  `restaurants`).
- **Изоляция.** Каждый контекст получает своего ACL-пользователя Valkey с доступом только к
  ключам с префиксом `<context>:`; отдельный инстанс на контекст — если этого требуют нагрузка
  или eviction policy. URL и credentials приходят из Secret, как у остальных хранилищ.
- **Конфиг обязателен, доступность — нет.** Контекст с кешем падает на старте при пустом или
  невалидном конфиге Valkey. Если Valkey недоступен во время работы, чтение идёт напрямую в
  хранилище: кеш только ускоряет, источник истины — база. Пока соединение не готово, кеш не
  ждёт Valkey; каждая команда ограничена коротким timeout, клиент переподключается сам. Обход
  кеша виден в метрике (`bypass`), а не только в логе. Readiness от Valkey не зависит. Промах
  (ключа нет, eviction, рестарт Valkey) — обычный cache-aside.

### Cache-aside с TTL

- Кешируется только query-сторона: результат чтения по ключу агрегата, проекции или страницы.
- Промах читает хранилище и кладёт результат с TTL. TTL обязателен для каждого ключа.
- Данные, которые меняются редко и допускают устаревание на TTL, кешируются **только с TTL**,
  без инвалидации: это первый вариант для любого кеша (каталог `restaurants`).
- Записи идут только в хранилище контекста. Сервис не пишет и не удаляет ключи кеша в
  обработчике команды: dual write «commit, потом `DEL`» теряет инвалидацию, если процесс упал
  между шагами.

### Инвалидация через Debezium CDC — когда TTL мало

Если окно TTL неприемлемо, а уменьшать TTL дальше бессмысленно, инвалидация вводится через уже
существующий CDC Outbox, а не кодом команды:

1. Команда в одной транзакции меняет агрегат и пишет запись Outbox с `aggregate_version`:
   integration event или служебное уведомление об изменении.
2. Debezium публикует запись в Kafka с ключом `aggregate_id`: порядок по агрегату сохраняется.
3. Invalidation consumer контекста-владельца (своя consumer group) записывает tombstone версии
   на ключи агрегата и зависящих от него представлений.

Запись кеша тогда хранит версию агрегата: заполнение и tombstone пишет атомарный Lua-скрипт,
заполнение не перезаписывает запись версии не меньше своей и tombstone более новой версии, так
чтение, начатое до изменения, не вернёт в кеш старое значение. Tombstone идемпотентен и монотонен по версии, поэтому повторы at-least-once безопасны без
Inbox. Пока Valkey недоступен, consumer не коммитит offset и повторяет запись с backoff: после
восстановления все пропущенные инвалидации применяются. Изменение закешированного агрегата без
записи Outbox недопустимо: такая запись добавляется, иначе агрегат не кешируется.

Окно устаревания = отставание CDC (alert `cdc-lag`, ADR 37) + время обработки consumer'а;
TTL — его верхняя граница при сбоях.

### Наблюдаемость и тесты

- Метрики `nomnom.cache.lookups` (`hit`/`miss`/`bypass`) и `nomnom.cache.errors` (по операции)
  по `nomnom.cache.name`; registry `ops/semconv`, инвентарь
  `ops/grafana/inventory`. Ключи и идентификаторы агрегатов не становятся labels.
- Интеграционные тесты поднимают настоящий Valkey через testcontainers: промах и запись с TTL,
  попадание, истечение TTL, отказ Valkey → чтение из базы; для кеша с инвалидацией — событие,
  повтор события и гонка «старое чтение после инвалидации». In-memory реализации кеша нет.

### Вне рамок

HTTP-кеширование, CDN, кеш ответов и persisted operations GraphQL-роутера (Cosmo) и кеш
клиента в UI решаются отдельно: они не хранят доменные данные контекста на стороне сервиса.

## Consequences

- Повторные чтения закешированных представлений не обращаются к хранилищу; после изменения
  они устаревают до TTL (с инвалидацией — на отставание CDC).
- Отказ Valkey не отказ операций: чтения уходят в базу, растут латентность и нагрузка на
  хранилище.
- Кеш только с TTL не добавляет ни записей Outbox, ни consumer'ов. Инвалидация, если она
  понадобится, использует существующий конвейер Outbox → Debezium → Kafka без кода в командах.
- Серверные метрики Valkey (память, evictions, соединения), панели кеша в дашбордах и alert на
  долю `bypass` — следующий шаг, пока их нет.
