# 40. Кеширование: пока без кеша, критерии ввода, Valkey + rueidis и инвалидация через CDC

Date: 2026-10-26

## Status

Accepted

Обобщает правило о кеше authorization-решений из
[18. SpiceDB for Authorization](0018-spicedb-for-authorization.md#failures-caching-и-observability)
на все контексты. Опирается на [17. Cloud-native runtime](0017-cloud-native-application-runtime.md),
[26. k6](0026-k6-for-performance-testing.md) и
[37. Доставка Outbox через Debezium CDC](0037-outbox-delivery-via-debezium-cdc.md).

## Context

В nomnom нет application-level кеша: сервисы читают из своих хранилищ (ADR 8), ни один
контекст не подключает Redis или Valkey. Возникает вопрос, не добавить ли кеш «заранее»,
например go-redis в `orders`.

Против этого:

- измеренного узкого места нет. Нагрузочные прогоны в kind дают только сравнительный сигнал
  (ADR 26), capacity-прогона в production-like окружении ещё не было;
- кеш — вторая копия данных с инвалидацией, окном устаревания и отдельными отказами. Без
  измеренного выигрыша это только расходы;
- правило проекта «без фолбеков» не позволяет молча обходить недоступный кеш и идти в базу:
  подключённый кеш становится обязательной зависимостью, а его отказ — отказом операции;
- в командах `orders` нужна согласованность агрегата (ADR 20, optimistic concurrency по
  `version`), а цены и состав заказа фиксируются в момент оформления. Устаревшее чтение
  здесь — ошибка, а не ускорение;
- Inbox, Outbox и идемпотентность уже транзакционно лежат в базе контекста (ADR 11, 13, 37).

При этом кандидаты на кеш есть: чтение каталога и меню (`restaurants` и BFF) — самый
нагруженный путь чтения, и небольшое устаревание там допустимо. Нужно заранее договориться,
когда и как кеш вводится, чтобы первый же кеш не появился как dual write с TTL «на глаз».

## Decision

### Сейчас кеша нет

Application-level кеш не вводится ни в одном контексте. Сервисы не подключают Valkey/Redis и
не держат in-process кеш доменных данных. Это не касается кешей сборки (ADR 10), registry-кеша
kind (ADR 34) и кешей, встроенных в используемые библиотеки (пулы соединений, prepared
statements).

### Критерии ввода

Кеш вводится только отдельным решением — локальным ADR контекста-владельца данных, — если
выполнены все условия:

1. **Измеренная причина.** Прогон k6 в production-like окружении (ADR 26) показывает, что
   конкретная операция не укладывается в свой SLO, и трассы указывают на чтение из хранилища.
   Результат kind причиной не считается.
2. **Дешёвые средства исчерпаны.** Индексы, план запроса, форма документа, проекция для
   чтения (CQRS, ADR 4 `orders`) и пул соединений уже проверены и не решают проблему.
3. **Данные допускают устаревание.** Для операции явно записаны допустимое окно устаревших
   данных и то, что видит пользователь внутри него.
4. **Решение описывает кеш полностью:** что кешируется, ключи и их кардинальность, TTL,
   источник инвалидации, окно устаревания (TTL + отставание CDC), поведение при отказе Valkey,
   метрики и ожидаемый hit ratio. После ввода повторный прогон k6 с зафиксированным состоянием
   кеша (cold/warm, ADR 26) показывает выигрыш; если его нет, кеш удаляется.

### Что не кешируется никогда

- Состояние, на которое опирается команда: агрегат внутри Unit of Work, цены и позиции,
  которые снимаются в заказ, проверки инвариантов. Команды читают только из хранилища.
- Inbox, Outbox, ключи идемпотентности, workflow state Temporal и любое другое durable
  state (ADR 17): потеря кеша не должна нарушать корректность.
- Чужие данные. Контекст кеширует только данные, которыми владеет; кеш не становится каналом
  интеграции и не читается другими контекстами (ADR 8).
- Authorization-решения SpiceDB — только по условиям ADR 18, отдельным решением.

### Технология при вводе

- **Сервер — [Valkey](https://valkey.io/)** (BSD-3-Clause, wire-совместим с Redis), а не Redis:
  лицензия Redis сменилась на RSAL/SSPL и затем AGPL. Версия — актуальная стабильная на
  момент ввода, совместимость подтверждается прогоном.
- **Go-клиент — [rueidis](https://github.com/redis/rueidis)**, а не go-redis: client-side
  caching поверх RESP3 `CLIENT TRACKING` (сервер сам рассылает инвалидацию локальных копий),
  автоматический pipelining и OpenTelemetry через `rueidisotel`. Клиенты для TS, Python и
  Rust выбираются локальным ADR контекста, который первым вводит кеш на этом языке; требования
  те же: RESP3, OpenTelemetry, работа с Valkey.
- **Изоляция.** Каждый контекст получает своего ACL-пользователя Valkey с доступом только к
  ключам с префиксом `<context>:`; отдельный инстанс на контекст — если этого требуют нагрузка
  или eviction policy. Endpoint и credentials приходят через runtime configuration, как у
  остальных хранилищ.
- **Обязательная зависимость.** Контекст, который использует кеш, падает на старте при пустом
  или невалидном конфиге Valkey. Недоступность Valkey во время работы — ошибка операции с
  bounded timeout и circuit breaker, а не обход кеша с чтением из базы. Промах (ключа нет,
  eviction, рестарт Valkey) — штатное поведение cache-aside, а не фолбек: значение читается из
  хранилища и кладётся в кеш.

### Шаблон: cache-aside на стороне чтения

- Кешируется только query-сторона: результат чтения по ключу агрегата или проекции.
- Записи идут только в хранилище контекста. Сервис не пишет и не удаляет ключи кеша в
  обработчике команды — dual write «commit, потом `DEL`» теряет инвалидацию, если процесс
  упал между шагами.
- Каждая запись в кеше содержит `aggregate_version`. Заполнение выполняет Valkey Function,
  которая не перезаписывает запись или tombstone с версией не меньше записываемой. Так чтение,
  начатое до изменения, не вернёт в кеш устаревшее значение после инвалидации.
- TTL обязателен для каждого ключа и ограничивает окно устаревания, даже если инвалидация
  отстаёт или потеряна.

### Инвалидация через Debezium CDC

Источник инвалидации — журнал базы через уже существующий CDC Outbox (ADR 37), а не код
команды:

1. Команда в одной транзакции меняет агрегат и пишет запись Outbox (integration event или
   Change Notification, ADR 36) с `aggregate_id` и `aggregate_version`.
2. Debezium публикует запись в Kafka с ключом `aggregate_id`: порядок по агрегату сохраняется.
3. Invalidation consumer контекста-владельца читает свои топики и для каждого события
   записывает tombstone с `aggregate_version` и коротким TTL на ключи этого агрегата и
   зависящих от него проекций.
4. Valkey рассылает tracking-инвалидацию; rueidis сбрасывает локальные копии в процессах.
   При разрыве соединения rueidis очищает локальный кеш целиком.

Операция идемпотентна и монотонна по версии, поэтому повторы at-least-once после рестарта
Connect безопасны без Inbox. Если изменение агрегата, попадающего в кеш, не порождает записи
Outbox, такая запись добавляется — без неё кешировать агрегат нельзя.

Окно устаревания = отставание CDC (alert `cdc-lag`, ADR 37) + время обработки consumer'а;
TTL — его верхняя граница при сбоях. Остановленный коннектор означает, что кеш устаревает до
TTL: допустимость этого записывается в решении о вводе кеша.

### Наблюдаемость и тесты

- Метрики клиента (`rueidisotel`: hit/miss, latency, ошибки) и Valkey (exporter: память,
  evictions, соединения) попадают в дашборды контекста и Platform / Overview как код (ADR 29).
  Ключи и идентификаторы агрегатов не становятся labels.
- Отставание invalidation consumer'а — метрика и alert контекста.
- Интеграционные тесты поднимают настоящий Valkey через testcontainers: промах и заполнение,
  инвалидация по событию, повтор события, гонка «старое чтение после инвалидации» (запись не
  перезаписывается), отказ Valkey → ошибка операции. In-memory реализации кеша нет.

### Вне рамок

HTTP-кеширование, CDN, кеш ответов и persisted operations GraphQL-роутера (Cosmo) и кеш
клиента в UI решаются отдельно: они не хранят доменные данные контекста на стороне сервиса.

## Consequences

- Сейчас в системе нет новой инфраструктуры и окна устаревших данных; все чтения строго из
  хранилищ. Производительность чтения определяют индексы, запросы и проекции.
- Первый кеш требует capacity-прогона k6 в production-like окружении. До него запросы «добавить
  Redis» отклоняются ссылкой на этот ADR.
- Когда кеш появится, Valkey станет обязательной зависимостью контекста: его отказ — отказ
  кешируемых операций, это закладывается в SLO и readiness.
- Инвалидация не требует кода в командах и использует существующий конвейер Outbox → Debezium →
  Kafka; цена — окно устаревания, зависящее от `cdc-lag`, и invalidation consumer в контексте.
- Выбор rueidis даёт двухуровневый кеш (Valkey + локальная копия) без собственной логики
  инвалидации локального слоя.
