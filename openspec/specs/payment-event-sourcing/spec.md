# payment-event-sourcing Specification

## Purpose
Определяет хранение `Payment` как потока событий: источник истины, конкурентную запись, синхронные проекции, версионирование событий и снапшоты. Решение описано в [локальном ADR 2 `payments`](../../../boundaries/payments/docs/adr/0002-event-sourcing-for-payment.md).

## Requirements

### Requirement: Поток событий — источник истины Payment
**ID:** FR-740

Состояние `Payment` и его `Payment Operation` SHALL восстанавливаться из потока событий этого `Payment`. На один `Payment` MUST приходиться один поток, а `Payment Operation` MUST быть частью агрегата `Payment`. Восстановление MUST NOT повторно записывать события для публикации или учитывать transitions FSM.

#### Scenario: Восстановление из потока
**ID:** AC-1017

- **GIVEN** `Payment` с записанным потоком событий
- **WHEN** `Payment` загружается
- **THEN** его состояние, Provider Reference и операции равны результату последовательного применения всех событий потока

#### Scenario: Неизвестный Payment
**ID:** AC-1018

- **WHEN** загружается `Payment` без потока и снапшота
- **THEN** результат — отсутствие `Payment`, а use case возвращает payment not found

#### Scenario: Восстановление без побочных эффектов
**ID:** AC-1019

- **WHEN** `Payment` восстанавливается из потока
- **THEN** у него нет новых событий для публикации и новых transitions FSM

### Requirement: Каждое изменение записывается событием
**ID:** FR-741

Каждое изменение `Payment` и `Payment Operation` SHALL записываться событием с данными, достаточными для восстановления состояния без других таблиц. Отсутствие результата provider MUST NOT создавать событий.

#### Scenario: Создание Payment
**ID:** AC-1020

- **WHEN** Create Payment создаёт `Payment`
- **THEN** поток начинается с `PaymentCreated` версии 1, а запись для публикации не создаётся

#### Scenario: Успешная Authorization
**ID:** AC-1021

- **WHEN** provider подтверждает Authorization
- **THEN** поток содержит `PaymentOperationRequested`, затем `PaymentOperationSucceeded`, затем `PaymentAuthorized` с Provider Reference

#### Scenario: Отказ в Authorization
**ID:** AC-1022

- **WHEN** provider отклоняет Authorization
- **THEN** поток содержит `PaymentOperationDeclined`, затем `PaymentFailed`

#### Scenario: Отмена Authorization очищает Provider Reference
**ID:** AC-1023

- **GIVEN** поток с `PaymentAuthorized`, за которым следует `PaymentAuthorizationCancelled`
- **WHEN** `Payment` восстанавливается
- **THEN** он находится в `pending` без Provider Reference

#### Scenario: Provider принял операцию асинхронно
**ID:** AC-1024

- **WHEN** provider отвечает, что результат придёт позже, или недоступен
- **THEN** в потоке остаётся только `PaymentOperationRequested` этой операции

### Requirement: Поток неизменяем
**ID:** FR-742

Хранилище SHALL разрешать только добавление событий. `UPDATE` и `DELETE` записанных событий MUST отклоняться на уровне схемы.

#### Scenario: Попытка изменить событие
**ID:** AC-1025

- **WHEN** выполняется `UPDATE` или `DELETE` строки `payment_events`
- **THEN** база отклоняет операцию ошибкой, строка не меняется

### Requirement: Конкурентная запись не теряет изменений
**ID:** FR-743

Версии событий одного потока SHALL идти подряд и быть уникальными. Запись на устаревшей версии MUST завершаться конфликтом версии, который Unit of Work повторяет по ADR 20 на заново загруженном состоянии. Ни один исход MUST NOT создавать второй финансовый эффект.

#### Scenario: Запись на устаревшей версии
**ID:** AC-1026

- **GIVEN** два экземпляра одного `Payment`, загруженные на одной версии
- **WHEN** оба записывают события
- **THEN** первая запись успешна, вторая завершается конфликтом версии и не оставляет событий

#### Scenario: Гонка операций с разными ключами
**ID:** AC-1027

- **WHEN** одновременно запрашиваются две операции одного `Payment` с разными idempotency key
- **THEN** ровно одна записывает `PaymentOperationRequested`, вторая отклоняется ошибкой operation in progress без обращения к provider

#### Scenario: Гонка с одним ключом
**ID:** AC-1028

- **WHEN** одновременно выполняются два запроса с одним idempotency key
- **THEN** в потоке один `PaymentOperationRequested`, и оба запроса относятся к одной `Payment Operation`

### Requirement: Проекции обновляются синхронно
**ID:** FR-744

`payments` и `payment_operations` SHALL обновляться в той же транзакции, что и запись событий, и MUST быть равны состоянию из потока. Уникальность `order_id` и `idempotency_key` между потоками MUST обеспечиваться индексами проекций, а её нарушение MUST откатывать события этой записи.

#### Scenario: Проекция равна потоку
**ID:** AC-1029

- **WHEN** Get Payment Status или List Payment Operations читает данные после любой завершённой записи
- **THEN** результат равен состоянию, восстановленному из потока

#### Scenario: Второй Payment того же Order
**ID:** AC-1030

- **WHEN** одновременно создаются два `Payment` одного `Order`
- **THEN** остаются один поток и одна строка проекции, а второй запрос получает уже созданный `Payment` по правилам `FR-400`

#### Scenario: Ключ занят другим Payment
**ID:** AC-1031

- **WHEN** запись операции нарушает уникальность `idempotency_key`
- **THEN** события этой записи не фиксируются, запрос отклоняется ошибкой idempotency key conflict без обращения к provider

### Requirement: Старые события остаются читаемыми
**ID:** FR-745

Каждое событие SHALL хранить явное имя типа и `schema_version`. Событие старой версии MUST приводиться к текущей upcaster'ом при чтении без изменения записанной строки. Неизвестный тип или неизвестная версия MUST приводить к ошибке загрузки; событие MUST NOT пропускаться.

#### Scenario: Записанный поток читается новым кодом
**ID:** AC-1032

- **GIVEN** зафиксированный в тестах поток прежней версии кода
- **WHEN** он загружается текущим кодом
- **THEN** состояние совпадает с ожидаемым

#### Scenario: Неизвестное событие
**ID:** AC-1033

- **WHEN** поток содержит неизвестный тип или версию события
- **THEN** загрузка завершается ошибкой, а состояние не строится

### Requirement: Снапшоты записываются по границе версий
**ID:** FR-746

`payments` SHALL записывать снапшот в той же транзакции, что и события, когда commit пересекает границу кратности `EVENT_STORE__SNAPSHOT_EVERY`, и MUST хранить только последний снапшот `Payment`. `EVENT_STORE__SNAPSHOT_EVERY` MUST быть положительным целым числом, иначе процесс MUST завершаться на старте. Ошибка записи снапшота MUST откатывать транзакцию.

#### Scenario: Граница не достигнута
**ID:** AC-1034

- **GIVEN** `EVENT_STORE__SNAPSHOT_EVERY = 5`
- **WHEN** commit доводит поток с версии 2 до версии 4
- **THEN** снапшот не записывается

#### Scenario: Commit перешагивает границу
**ID:** AC-1035

- **GIVEN** `EVENT_STORE__SNAPSHOT_EVERY = 5`
- **WHEN** commit из двух событий доводит поток с версии 4 до версии 6
- **THEN** записывается снапшот версии 6, заменяя предыдущий снапшот этого `Payment`

#### Scenario: Откат записи
**ID:** AC-1036

- **WHEN** транзакция с событиями и снапшотом откатывается
- **THEN** ни события, ни снапшот не сохраняются

#### Scenario: Невалидная настройка
**ID:** AC-1037

- **WHEN** `EVENT_STORE__SNAPSHOT_EVERY` пуст, не является целым числом или меньше 1
- **THEN** процесс завершается на старте и не открывает порты

### Requirement: Снапшот ускоряет загрузку и не меняет результат
**ID:** FR-747

Загрузка SHALL использовать снапшот текущей версии схемы и применять только события после него. Результат MUST быть равен полному replay. Снапшот MUST быть производными данными: его отсутствие и другая версия схемы MUST приводить к сборке из всего потока, а нечитаемый снапшот текущей версии MUST приводить к ошибке загрузки.

#### Scenario: Загрузка со снапшотом
**ID:** AC-1038

- **GIVEN** снапшот версии 5 и поток из 7 событий
- **WHEN** `Payment` загружается
- **THEN** применяются только события версий 6 и 7, а состояние равно полному replay потока

#### Scenario: Снапшот удалён
**ID:** AC-1039

- **WHEN** снапшоты удалены и `Payment` загружается
- **THEN** состояние собирается из всего потока, а данные не теряются

#### Scenario: Другая версия схемы снапшота
**ID:** AC-1040

- **GIVEN** снапшот с другой версией схемы
- **WHEN** `Payment` загружается и следующий commit пересекает границу
- **THEN** загрузка использует весь поток, а снапшот перезаписывается текущей версией

#### Scenario: Нечитаемый снапшот
**ID:** AC-1041

- **WHEN** снапшот текущей версии схемы нельзя разобрать
- **THEN** загрузка завершается ошибкой, а состояние не строится

### Requirement: Integration Events не меняются
**ID:** FR-748

Контракты, топик и Outbox Integration Events `payments` SHALL оставаться прежними. Новые события потока и Provider Reference MUST NOT публиковаться. `aggregate_version` MUST быть версией потока после commit и MUST расти между commit одного `Payment`; рост на 1 MUST NOT гарантироваться.

#### Scenario: Публикация успешной Authorization
**ID:** AC-1042

- **WHEN** commit записывает `PaymentOperationSucceeded` и `PaymentAuthorized`
- **THEN** в Outbox появляется только прежний контракт `PaymentAuthorized` без Provider Reference, его `aggregate_version` равна версии потока после commit

#### Scenario: Запрос операции
**ID:** AC-1043

- **WHEN** commit записывает только `PaymentOperationRequested`
- **THEN** запись в Outbox не создаётся

### Requirement: Payment без потока недопустим
**ID:** FR-749

Миграция на поток событий SHALL завершаться ошибкой, если `payments` содержит строки. Перенос существующих `Payment` MUST NOT выполняться.

#### Scenario: Непустая таблица
**ID:** AC-1044

- **GIVEN** `payments` содержит строки без потока
- **WHEN** процесс применяет миграцию при старте
- **THEN** миграция завершается ошибкой, и процесс не стартует
