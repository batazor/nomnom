# Design

## Списки слайсов

Каждый слайс объявляет список рядом с регистрацией и проверяет ключи по своему cradle:

```ts
export const MENU_USE_CASES = {
  getMenu: query("get_menu"),
  createMenu: command("create_menu"),
  // ...
} as const satisfies Partial<Record<keyof MenuCradle, UseCase>>;
```

`satisfies` даёт ошибку компиляции при опечатке в ключе, поэтому она не доходит до старта процесса.

Распределение повторяет владельцев handlers. Сегодняшние `RESTAURANTS_USE_CASES` и `CONSUMER_USE_CASES` делятся по регистрациям:

| Слайс | Use cases |
| --- | --- |
| `restaurant` | карточка ресторана, расписание, настройки запланированных заказов, персонал, открытие и закрытие |
| `menu` | чтение и изменение меню |
| `restaurantorder` | приём заказа, команды кухни, Record Pickup, запланированные заказы |
| `scheduleslot` | окна и резервации |
| `cook` | пул поваров |
| `simulator` | чтение и переключение Simulator |

`record_wait_time` работает только в `cmd/restaurants-consumer`, поэтому слайс-владелец экспортирует для него отдельный список. Процесс HTTP/gRPC этот сценарий не инструментирует, как и сегодня.

## Композиция

`instrumentUseCases` остаётся в `di/usecases.ts`: он работает с контейнером процесса. Списки собираются там, где процесс регистрирует слайсы:

```ts
instrumentUseCases(container, {
  ...RESTAURANT_USE_CASES,
  ...MENU_USE_CASES,
  // ...
});
```

Порядок и момент вызова не меняются: декоратор применяется после регистрации слайсов. Незарегистрированный ключ по-прежнему роняет процесс на старте. Импорт `command` и `query` из `pkg/telemetry/usecase.ts` в `di` слайса разрешён правилами зависимостей.

## Проверка эквивалентности

Перенос не должен менять набор инструментированных сценариев. Это проверяет `test/composition.test.ts`: тест сверяет объединённые списки с фиксированным перечнем сегодняшних имён (`AC-996`). После проверки перечень остаётся как регрессионный тест, а новый сценарий дописывает в него своё имя.
